# Умный кредитный кабинет предпринимателя

Прототип цифрового кредитного конвейера для малого и микробизнеса: **кабинет клиента** и **рабочее место банка** в одной системе, связанные одной заявкой со строгой машиной состояний. Трек «Умный кредитный кабинет предпринимателя», Альфа-Будущее Хакатон 2026.

> Демо-стенд. Все данные синтетические; БКИ, ЕГРЮЛ/ЕГРИП и ФНС «Прозрачный бизнес» — **моки**; подписание — имитация простой ЭП (код в интерфейсе); выдача — моделируемая, реальных денежных операций нет. Все пороги и ставки — допущения команды, см. [docs/assumptions.md](docs/assumptions.md).

## Запуск (одна команда)

Требуется Docker 24+ (≈ 300 МБ на образ, ≈ 100 МБ ОЗУ).

```bash
docker compose up --build --wait
```

Откройте <http://localhost:8000>. Порт и ключевая ставка меняются через `.env` (см. `.env.example`). Данные хранятся в томе `data` и переживают перезапуск; сброс — кнопкой «Пульт стенда» (админ) или `docker compose down -v`.

Без Docker (Python 3.12+):

```bash
pip install -r requirements-dev.txt
uvicorn app.main:app --port 8000        # UI и API на одном порту
pytest -q                               # ядро решения, каскад, сквозные сценарии через HTTP (ML-тесты пропускаются без LightGBM)
```

Публичное демо на бесплатном хостинге (Render) — как развернуть: [docs/deploy.md](docs/deploy.md); оно дополняет локальный запуск, а не заменяет его.

OpenAPI/Swagger: <http://localhost:8000/docs> · схема: `/openapi.json` · коллекция запросов: [docs/api-examples.http](docs/api-examples.http).

## Учётные записи (пароль у всех: `demo123`)

| Логин | Роль | Что показывает |
|---|---|---|
| `sever` | клиент, ООО «Север-Тех» | **одобрение** как запрошено (95 баллов, грейд A), предодобрение, льготная программа K+3, подпись и выдача |
| `lesnoy` | клиент, ООО «Лесной хлеб» | **встречное предложение**: на 12 мес. платёж не проходит → «та же сумма на 24 мес.» |
| `gromov` | клиент, ИП Громов А. С. | **сбой БКИ → ручной разбор → запрос выписки → решение** (деградация вместо отказа) |
| `stroy` | клиент, ООО «СтройРесурс» | **отказ** по стоп-правилу (налоговая недоимка) с понятной причиной |
| `analyst` | сотрудник банка | очередь, карточка заявки, скоринг по факторам, решение на ручном разборе |
| `admin` | администратор | всё то же + пульт: ключевая ставка, режим БКИ, скорость конвейера, сброс данных |

## Проверка за 5 минут

1. **Вход `sever`** → «Оформить» оборотный кредит → 3 000 000 ₽ на 24 мес. (калькулятор пересчитывает платёж на лету) → согласия → отправить. Статус меняется сам: *Проверяем → Оцениваем → Предложение готово*. Принять → ввести код (показан на экране) → *Кредит выдан*, договор, график платежей, CSV.
2. **Вход `lesnoy`** → оборотный кредит 3 000 000 ₽ на **12** мес. → «Одобрено на других условиях»: **24 мес., 19,0 %, платёж 151 226 ₽**; блок «Почему такое решение» и сравнение «как просили → как предлагаем».
3. **Вход `gromov`** → оборотный кредит 400 000 ₽ на 12 мес. → «Заявку рассматривает специалист». В другом окне **вход `analyst`** → очередь → заявка → видны источники (БКИ недоступно), частичный скоринг и журнал → «Запросить документы». Вернитесь в кабинет `gromov` → «Подключить выписку» → БКИ отвечает, итог: грейд C, 62 балла, ставка 20,5 %.
4. **Вход `stroy`** → любая заявка → отказ с причиной «задолженность по налогам» и подсказкой «что можно сделать». Аналитик видит сработавшее правило H06; скоринг не считался.
5. **Вход `admin`** → «Пульт стенда» → БКИ «Сбой» → заявка любого клиента уходит на ручной разбор вместо отказа; ключевая ставка 16 % → цены пересчитываются (ставка фиксируется в оферте).

## Как это устроено

```
Браузер (статический UI, без сборки) ──► FastAPI ──► SQLite (WAL)
   кабинет клиента / рабочее место банка     │  машина состояний, журнал событий (одна транзакция)
                                             ├─ scoring.py  — карта 14 факторов, 100 баллов, стоп-правила
                                             ├─ policy.py   — допуск, P_max по DSCR, цена, встречное предложение, маршрут
                                             ├─ pricing.py  — формула ставки, аннуитет, график
                                             └─ mocks.py    — БКИ / ЕГРЮЛ / ФНС / данные банка (синтетика, сбои)
```

* **Скоринг ≠ решение.** Скоринг оценивает риск клиента (не зависит от суммы). Политика решает по заявке: допуск продукта → платёжеспособность (DSCR) → цена → как просили / больший срок / меньшая сумма / отказ → автомат или ручной разбор.
* **Объяснимость.** Причина = потерянные баллы фактора; одни и те же коды причин (R01–R19) питают клиентский текст и экран аналитика. Формулировки не раскрывают пороги и антифрод.
* **Один продукт — две стороны.** Таблица `events` — единый журнал; клиент видит свой срез, банк — полный (включая ответы источников и повторы).
* **Надёжность.** Переходы только по таблице разрешённых ([docs/state-diagram.md](docs/state-diagram.md)); оптимистичная блокировка `version`; `Idempotency-Key` на создании заявки; недоступность БКИ → ручной разбор, а не отказ; изоляция данных клиентов; роли `client` / `analyst` / `admin`.
* **Политика в конфиге.** [config/products.yaml](config/products.yaml): продукты, формула цены, грейды, DSCR. Ключевая ставка — параметр (`KEY_RATE`, пульт); снимок ставки хранится в оферте.

Подробнее: [модель процесса](docs/process-model.md) · [архитектура и ER](docs/architecture.md) · [диаграмма состояний](docs/state-diagram.md) · [кредитная политика](docs/credit-policy.md) · [ML-слой](docs/ml.md) · [тестовые сценарии](docs/test-scenarios.md) · [допущения](docs/assumptions.md) · [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md). ## ML-слой: PD-модель и каскад по продуктам (опционально)

Над правилами есть второй режим решения (`ml_cascade`, переключатель в пульте администратора): **одна модель градиентного бустинга (LightGBM) на все продукты** оценивает PD конкретного предложения, а для каждого продукта два порога дают три зоны — **автоодобрение / серая зона / пропуск продукта**. Серая зона: сначала пробуются более безопасные продукты каскада (оборотный → овердрафт), иначе заявку берёт живой верификатор с готовой рекомендацией; если пропущены все продукты — отказ. Жёсткие стоп-правила стоят до модели.

* Скрипты: [`ml/train.py`](ml/train.py) (обучение, калибровка, метрики, таблица зон), [`ml/predict.py`](ml/predict.py) (инференс, SHAP-вклады, батч-скоринг CSV), [`ml/features.py`](ml/features.py), [`ml/synth.py`](ml/synth.py) (синтетика **только для проверки конвейера**).
* Обученной боевой модели в репозитории нет — данных банка нет. Без модели PD считается по скоркарте, и всё работает (источник PD виден в пульте и в карточке заявки).
* Подробно — цели, таргет, признаки, каскад, практика, ограничения: [docs/ml.md](docs/ml.md).

```bash
docker build -f ml/Dockerfile -t credit-ml .                                       # окружение с LightGBM
docker run --rm -v "$PWD":/work -w /work credit-ml pytest -q                       # все тесты, включая обучение и предикт
WITH_ML=1 DECISION_MODE=ml_cascade docker compose up --build --wait                # приложение с инференсом модели из ./models/pd_current
```

## Что не вошло в эту версию (и почему)

LLM-функции (подбор продукта «своими словами»), прогноз кассового разрыва и разбор выписок — ядро детерминированное и проверяемое, ИИ заложен как опциональный слой в roadmap; настоящие ЭП и интеграции; кредитный комитет (вместо него поле `second_approver_required`); мобильная адаптация сверх базовой; PostgreSQL (схема совместима, в проде заменить SQLite).
