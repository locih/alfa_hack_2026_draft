# Умный кредитный кабинет предпринимателя

Прототип цифрового кредитного конвейера для малого и микробизнеса: **кабинет клиента** и **рабочее место банка** в одной системе, связанные одной заявкой со строгой машиной состояний. Трек «Умный кредитный кабинет предпринимателя», Альфа-Будущее Хакатон 2026.

> Демо-стенд. Все данные синтетические; БКИ, ЕГРЮЛ/ЕГРИП и ФНС «Прозрачный бизнес» — **моки**; подписание — имитация простой ЭП (код в интерфейсе); выдача — моделируемая, реальных денежных операций нет. Все пороги и ставки — допущения команды ([docs/assumptions.md](docs/assumptions.md)).

## Запуск (одна команда)

Требуется Docker 24+ (≈ 300 МБ на образ, ≈ 100 МБ ОЗУ). LLM и внешние сервисы не нужны, интернет при работе не используется.

```bash
docker compose up --build --wait
```

Откройте <http://localhost:8000>. Порт, ключевая ставка и пауза между этапами конвейера задаются через `.env` (см. `.env.example`). Данные хранятся в томе `data` и переживают перезапуск; сброс — кнопкой в «Пульте стенда» (админ) или `docker compose down -v`.

Без Docker (Python 3.12+):

```bash
pip install -r requirements-dev.txt
uvicorn app.main:app --port 8000        # UI и API на одном порту
pytest -q                               # ядро решения, каскад, сквозные сценарии через HTTP
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `8000` | порт (на PaaS задаётся платформой) |
| `KEY_RATE` | `14.0` | ключевая ставка, % — от неё считаются все цены |
| `STEP_DELAY_SEC` | `1.2` | пауза между автоэтапами конвейера (для наглядности демо; `0` — мгновенно) |
| `DECISION_MODE` | `rules` | `rules` или `ml_cascade` (также переключается в пульте администратора) |
| `DB_PATH` | `/data/app.db` | файл SQLite |
| `MODEL_DIR` | `/models/pd_current` | каталог обученной PD-модели (необязательно) |

Публичное демо на бесплатном хостинге (Render): [docs/deploy.md](docs/deploy.md) — оно дополняет локальный запуск, а не заменяет его. OpenAPI/Swagger: <http://localhost:8000/docs>.

## Учётные записи (пароль у всех: `demo123`)

| Логин | Роль | Что показывает |
|---|---|---|
| `sever` | клиент, ООО «Север-Тех» | **одобрение** как запрошено (95 баллов, грейд A), предодобрение, льготная программа K+3, подпись и выдача |
| `lesnoy` | клиент, ООО «Лесной хлеб» | **встречное предложение**: на 12 мес. платёж не проходит → «та же сумма на 24 мес.» |
| `gromov` | клиент, ИП Громов А. С. | **сбой БКИ → ручной разбор → запрос выписки → решение** (деградация вместо отказа) |
| `stroy` | клиент, ООО «СтройРесурс» | **отказ** по стоп-правилу (налоговая недоимка) с понятной причиной |
| `analyst` | сотрудник банка | очередь, карточка заявки, скоринг по факторам, решение на ручном разборе |
| `admin` | администратор | всё то же + пульт: ключевая ставка, режим БКИ, режим решения, скорость конвейера, сброс данных |

## Проверка за 5 минут

1. **Вход `sever`** → «Оформить» оборотный кредит → 3 000 000 ₽ на 24 мес. (калькулятор пересчитывает платёж на лету) → согласия → отправить. Статус меняется сам: *Проверяем → Оцениваем → Предложение готово*. Принять → ввести код (показан на экране) → *Кредит выдан*, договор, график платежей, CSV.
2. **Вход `lesnoy`** → оборотный кредит 3 000 000 ₽ на **12** мес. → «Одобрено на других условиях»: **24 мес., 19,0 %, платёж 151 226 ₽**; сверху главные цифры, ниже «Почему такое решение» и сравнение «как просили → как предлагаем».
3. **Вход `gromov`** → оборотный кредит 400 000 ₽ на 12 мес. → «Заявку рассматривает специалист». В другом окне **вход `analyst`** → очередь → заявка → видны источники (БКИ недоступно), частичный скоринг и журнал → «Запросить документы». Вернитесь в кабинет `gromov` → «Подключить выписку» → БКИ отвечает, итог: грейд C, 62 балла, ставка 20,5 %, платёж 37 150 ₽.
4. **Вход `stroy`** → любая заявка → отказ с причиной «задолженность по налогам» и подсказкой «что можно сделать». Аналитик видит сработавшее правило H06; скоринг не считался.
5. **Вход `admin`** → «Пульт стенда» → БКИ «Сбой» → заявка любого клиента уходит на ручной разбор вместо отказа; ключевая ставка 16 % → цены пересчитываются (ставка фиксируется в оферте).

Полный список сценариев с ожидаемыми цифрами: [docs/test-scenarios.md](docs/test-scenarios.md).

## Что умеет продукт

**Кабинет клиента** (для владельца, директора, бухгалтера без банковской экспертизы):
* **Главная:** что банк уже знает о бизнесе (данные из реестров и банка — вводить повторно не нужно), график поступлений за 12 месяцев, **предодобрение** по каждому продукту («до X ₽, ставка от Y %», с оговоркой «не гарантия»), активная заявка и «что нужно от вас».
* **Новая заявка в 3 шага:** цель и подбор продукта (с рекомендацией) → сумма и срок с калькулятором «что если» (платёж, переплата, помещается ли в платёжеспособность, максимальная сумма) → проверка данных и согласия (ПДн, БКИ, ФНС).
* **Страница заявки:** статус простыми словами, блоки **«что дальше / что нужно от вас / когда»**, пять нейтральных шагов, предложение с главными цифрами (платёж, ставка, срок), сравнение «как просили → как предлагаем», «почему такое решение» и «что можно сделать», подпись кодом, договор и график платежей (CSV). История и график свёрнуты — детали по запросу. Клиент **не видит** внутренние этапы банка, баллы, грейды, стоп-правила и ответы источников.
* **Запрос документов:** понятный список «что нужно от вас» (в демо выписка подключается кнопкой).

**Рабочее место банка** (аналитик):
* **Очередь** с фильтрами (ручной разбор, ждём клиента, в работе, завершённые), счётчиками и оценкой по каждой заявке.
* **Карточка заявки:** запрос и клиент, ответы источников с временем, **разбор по 14 факторам** скоринга (полосы баллов), стоп-правила и флаги, расчёт максимального платежа «как посчитано», рекомендация системы, журнал событий (включая то, чего не видит клиент).
* **Решение аналитика:** одобрить или изменить условия (цена считается по формуле, платёж выше расчётного максимума требует комментария), запросить документы, отказать (обязательны причины из справочника).
* **Пульт администратора:** ключевая ставка, режим БКИ (сбой), режим решения, скорость конвейера, сброс данных.

## Продукты и цены

Четыре продукта и две механики расчёта (аннуитет и лимит). Параметры — в [config/products.yaml](config/products.yaml).

| Продукт | Сумма | Срок | Механика | Обеспечение | Допуск |
|---|---|---|---|---|---|
| Оборотный кредит | 100 тыс. – 5 млн ₽ | 6–36 мес. | аннуитет | нет / поручительство / недвижимость | бизнесу от 6 мес. |
| Овердрафт | лимит 100 тыс. – 3 млн ₽ (≤ 50 % среднемесячных поступлений) | 12 мес., транш до 60 дней | лимит, плата за установление 1,5 % | нет / поручительство | клиент банка от 6 мес. |
| Кредит на развитие | 1 – 15 млн ₽ | 12–60 мес. | аннуитет | залог приобретаемого актива | бизнесу от 12 мес. |
| Льготный оборотный (господдержка) | 500 тыс. – 5 млн ₽ | 12–36 мес. | аннуитет, ставка **K + 3 п.п.** | как у оборотного | реестр МСП и приоритетная отрасль |

**Формула цены** (единая, от ключевой ставки K):

`ставка = округление_вверх_до_0,5( K + OpEx + PD × LGD + плата за капитал + маржа + надбавка продукта + надбавка за срок )`, потолок `K + 10 п.п.`

Ставки при K = 14 % (без обеспечения, автоматическое решение):

| Грейд | Оборотный ≤ 12 мес. | Оборотный 13–36 мес. | Овердрафт | Развитие (залог оборудования) 13–36 мес. | Льготный |
|---|---|---|---|---|---|
| A | 17,5 % | 18,0 % | 18,5 % | 18,5 % | 17,0 % |
| B | 18,5 % | 19,0 % | 19,5 % | 19,5 % | 17,0 % |
| C | 20,5 % | 21,0 % | 21,5 % | 20,5 % | 17,0 % |
| D | только ручной разбор, до 24,0 % | | | | — |

Изменение ключевой ставки пересчитывает все цены; в оферте хранится снимок ставки. Залог в модели скорее **открывает доступ** (лимиты, срок), чем сильно удешевляет. Подробно: [docs/credit-policy.md](docs/credit-policy.md).

## Процесс и статусы

Пять шагов для клиента, 12 внутренних статусов и 26 разрешённых переходов ([диаграмма](docs/state-diagram.md), [модель процесса](docs/process-model.md)):

| Шаг | Статусы | Что происходит |
|---|---|---|
| 1. Заявка | DRAFT | создание заявки (идемпотентно), согласия |
| 2. Проверка | VERIFICATION, AWAITING_DOCS | допуск и стоп-правила, запросы в ЕГРЮЛ, ФНС, БКИ (таймаут, 2 повтора), данные банка; при нехватке данных — запрос документов |
| 3. Решение | DECISIONING, MANUAL_REVIEW, OFFER_READY, DECLINED | скоринг, платёжеспособность, цена; как просили / встречное / ручной разбор / отказ |
| 4. Подписание | AWAITING_SIGNATURE | код подтверждения (имитация простой ЭП) |
| 5. Выдача | DISBURSING, DISBURSED | договор, график платежей, моделируемое зачисление |

Завершения без выдачи: DECLINED (отказ), WITHDRAWN (клиент отозвал или отказался от предложения), EXPIRED (истёк срок документов, оферты или подписания).

## Скоринг и решение

* **Скоринг ≠ решение.** Скоринг оценивает риск клиента (14 факторов, 100 баллов, не зависит от суммы): бизнес и данные 25, денежный поток 33, кредитная история 30, налоги и репутация 12. Грейды: A ≥ 80, B ≥ 65, C ≥ 50, D ≥ 35, E < 35. Возраст, пол, семейное положение и регион владельца не используются.
* **Стоп-правила** (скоринг не считается): возраст бизнеса < 6 мес., банкротство, недостоверность ЕГРЮЛ, блокировка счетов, налоговая недоимка, текущая просрочка, иски > 5 % оборота, санкционный флаг.
* **Политика по заявке:** допуск продукта → платёжеспособность `P_max = ЧДП / DSCR − текущие платежи` (DSCR 1,25 / 1,30 / 1,40 / 1,60 для A–D) → цена → **как просили → больший срок → меньшая сумма → отказ**. Автоматическое решение — при грейде A–C, данных БКИ, менее двух флагах и сумме в автолимите; иначе ручной разбор.
* **Объяснимость:** причина = потерянные баллы фактора; одни и те же коды (R01–R20) питают клиентский текст и экран аналитика. Формулировки не раскрывают пороги и антифрод.
* **Деградация вместо отказа:** недоступный источник данных переводит заявку на ручной разбор.

## Архитектура

```
Браузер (статический UI, без сборки) ──► FastAPI ──► SQLite (WAL)
   кабинет клиента / рабочее место банка     │  машина состояний, журнал событий (одна транзакция)
                                             ├─ scoring.py  — карта 14 факторов, стоп-правила
                                             ├─ policy.py   — допуск, P_max по DSCR, цена, встречное предложение, маршрут
                                             ├─ pricing.py  — формула ставки, аннуитет, график
                                             ├─ mocks.py    — БКИ / ЕГРЮЛ / ФНС / данные банка (синтетика, управляемые сбои)
                                             └─ cascade.py + pd_provider.py — опциональный ML-слой
```

* **Один продукт — две стороны.** Таблица `events` — единый журнал; клиент видит свой срез, банк — полный.
* **Надёжность и безопасность:** переходы только по таблице; оптимистичная блокировка `version`; `Idempotency-Key` при создании заявки; роли `client` / `analyst` / `admin` и изоляция данных клиентов; пароли PBKDF2, токены сессий; не-root контейнер, healthcheck; статика всегда перепроверяется (`Cache-Control: no-cache`).
* **Политика в конфиге:** продукты, формула цены, грейды, DSCR — [config/products.yaml](config/products.yaml); версии карты и политики пишутся в каждое решение.

Подробнее: [docs/architecture.md](docs/architecture.md) (контейнеры, последовательность, ER-модель, что менять в проде).

## Тесты и проверка цифр

* `pytest -q` — ядро скоринга, цены и политики, сквозные сценарии четырёх клиентов через HTTP, права доступа, идемпотентность, отсутствие внутренних данных в клиентских ответах, каскад. Тесты ML-конвейера требуют LightGBM и выполняются в контейнере `ml/Dockerfile`.
* `python tests/verify_numbers.py` — независимая сверка цен (1120 комбинаций продукт × грейд × срок × обеспечение), аннуитета, графика платежей и `P_max` с формулами из документации.

## ML-слой (опционально)

Второй режим решения `ml_cascade`: одна модель градиентного бустинга (LightGBM) на все продукты оценивает PD конкретного предложения, по двум порогам продукта — автоодобрение, серая зона (сначала более безопасные продукты, иначе живой верификатор) или пропуск продукта. Стоп-правила стоят до модели. **Обученной боевой модели в репозитории нет** (данных банка нет): без неё PD считается по скоркарте, и всё работает; скрипты обучения и предикта ([`ml/train.py`](ml/train.py), [`ml/predict.py`](ml/predict.py)) проверены на синтетике. Подробно: [docs/ml.md](docs/ml.md).

```bash
WITH_ML=1 DECISION_MODE=ml_cascade docker compose up --build --wait   # приложение с инференсом модели из ./models/pd_current
docker build -f ml/Dockerfile -t credit-ml . && docker run --rm -v "$PWD":/work -w /work credit-ml pytest -q   # все тесты, включая ML
```

## Что не вошло в эту версию (и почему)

LLM-функции (подбор продукта «своими словами»), прогноз кассового разрыва и разбор выписок — ядро детерминированное и проверяемое, ИИ заложен как опциональный слой в roadmap; настоящие ЭП и интеграции; кредитный комитет (вместо него поле `second_approver_required`); пост-кредитное обслуживание; PostgreSQL (схема совместима, в проде заменить SQLite). Источники допущений и ограничения — [docs/assumptions.md](docs/assumptions.md).
