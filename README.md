# Умный кредитный кабинет предпринимателя

Прототип кредитного конвейера для малого и микробизнеса. В одной системе два экрана: кабинет клиента и рабочее место банка. Оба работают с одной и той же заявкой, а её статус может меняться только по заранее заданным переходам. Решение для трека «Умный кредитный кабинет предпринимателя», Альфа-Будущее Хакатон 2026.

> Это демо-стенд. Все данные синтетические. БКИ, ЕГРЮЛ/ЕГРИП и ФНС «Прозрачный бизнес» заменены моками. Подписание имитируется кодом на экране, выдача только записывается в систему, настоящих денег нет. Пороги и ставки мы выбрали сами; откуда они, написано в [docs/assumptions.md](docs/assumptions.md).

## Запуск (одна команда)

Нужен Docker 24+: образ занимает около 300 МБ, приложению хватает 100 МБ памяти. LLM, внешние сервисы и интернет не требуются.

```bash
docker compose up --build --wait
```

Откройте <http://localhost:8000>. Порт, ключевую ставку и паузу между этапами можно поменять в `.env` (образец — `.env.example`). Данные лежат в томе `data` и переживают перезапуск. Сбросить их можно кнопкой в «Пульте стенда» под админом или командой `docker compose down -v`.

Без Docker (Python 3.12+):

```bash
pip install -r requirements-dev.txt
uvicorn app.main:app --port 8000        # UI и API на одном порту
pytest -q                               # тесты ядра, каскада и сквозных сценариев
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `8000` | порт (на PaaS задаётся платформой) |
| `KEY_RATE` | `14.0` | ключевая ставка, % — от неё считаются все цены |
| `STEP_DELAY_SEC` | `1.2` | пауза между автоэтапами конвейера (для наглядности демо; `0` — мгновенно) |
| `DECISION_MODE` | `rules` | `rules` или `ml_cascade` (также переключается в пульте администратора) |
| `DEMO_MODE` | `1` | при `0` с экрана входа пропадают список демо-учёток и пароль (нужно, если стенд не для демонстрации) |
| `DB_PATH` | `/data/app.db` | файл SQLite |
| `MODEL_DIR` | `/models/pd_current` | каталог обученной PD-модели (необязательно) |

Как выложить публичное демо на бесплатный хостинг (Render), описано в [docs/deploy.md](docs/deploy.md). Оно дополняет локальный запуск и не заменяет его. Swagger: <http://localhost:8000/docs>.

## Проверка за 5 минут

1. **Вход `sever`** → «Оформить» оборотный кредит → 3 000 000 ₽ на 24 мес. (калькулятор пересчитывает платёж на лету) → согласия → отправить. Статус меняется сам: *Проверяем → Оцениваем → Предложение готово*. Принять → ввести код (показан на экране) → *Кредит выдан*, договор, график платежей, CSV.
2. **Вход `lesnoy`** → оборотный кредит 3 000 000 ₽ на **12** мес. → «Одобрено на других условиях»: **24 мес., 19,0 %, платёж 151 226 ₽**; сверху главные цифры, ниже «Почему такое решение» и сравнение «как просили → как предлагаем».
3. **Вход `gromov`** → оборотный кредит 400 000 ₽ на 12 мес. → «Заявку рассматривает специалист». В другом окне **вход `analyst`** → очередь → заявка → видны источники (БКИ недоступно), частичный скоринг и журнал → «Запросить документы». Вернитесь в кабинет `gromov` → «Подключить выписку» → БКИ отвечает, итог: грейд C, 62 балла, ставка 20,5 %, платёж 37 150 ₽.
4. **Вход `stroy`** → любая заявка → отказ с причиной «задолженность по налогам» и подсказкой «что можно сделать». Аналитик видит сработавшее правило H06; скоринг не считался.
5. **Вход `admin`** → «Пульт стенда» → БКИ «Сбой» → заявка любого клиента уходит на ручной разбор вместо отказа; ключевая ставка 16 % → цены пересчитываются (ставка фиксируется в оферте).

Полный список сценариев с ожидаемыми цифрами: [docs/test-scenarios.md](docs/test-scenarios.md).

## Что умеет продукт

**Кабинет клиента.** Рассчитан на владельца, директора или бухгалтера, которые не разбираются в банковских процессах.
* Главная. Показывает, что банк уже знает о бизнесе, поэтому данные повторно вводить не нужно. Там же график поступлений за 12 месяцев, предодобрение по каждому продукту («до X ₽, ставка от Y %», с пометкой «не гарантия») и текущая заявка.
* Новая заявка в три шага. Сначала цель и подбор продукта, затем сумма и срок с калькулятором «что если» (платёж, переплата, помещается ли платёж в денежный поток, максимальная сумма), затем проверка данных и согласия на обработку ПДн, запрос в БКИ и ФНС.
* Страница заявки. Статус описан обычными словами, под ним три блока: «что дальше», «что нужно от вас», «когда». Ниже предложение с главными цифрами (платёж, ставка, срок), сравнение «как просили — как предлагаем», причины решения и подсказки, что можно изменить. Потом подпись кодом, договор и график платежей с выгрузкой в CSV. История и график свёрнуты, их можно раскрыть. Внутренние этапы банка, баллы, грейды, стоп-правила и ответы источников клиент не видит.
* Запрос документов. Клиент видит список «что нужно от вас». В демо выписка подключается кнопкой.
* «Мой кредит». Это необязательный модуль: по ответам вебинара обслуживание после выдачи не входит в базовый объём, и основной процесс от него не зависит. После выдачи видны остаток долга, доля погашенного, выплаченные проценты и ближайший платёж. Есть демо-счёт с кнопкой «Пополнить счёт» и кнопка «Оплатить платёж»: она списывает платёж со счёта и уменьшает долг. В графике платежей указаны номер, дата, основной долг, проценты, сумма платежа и остаток, у оплаченных строк стоит галочка, внизу строка «Итого». Все операции условные.
* Подсказки к терминам. Слова вроде «ставка», «аннуитет», «поручительство» и «простая электронная подпись» подчёркнуты, пояснение появляется при наведении, фокусе с клавиатуры или касании. На экране подписания есть короткая сводка «что вы подписываете».

**Рабочее место банка** (для аналитика).
* Очередь заявок с фильтрами (ручной разбор, ждём клиента, в работе, завершённые), счётчиками и оценкой по каждой заявке.
* Карточка заявки: запрос и данные клиента, ответы источников со временем, разбор скоринга по 14 факторам, стоп-правила и флаги, расчёт максимального платежа, рекомендация системы и журнал событий, включая то, что клиент не видит.
* Решение аналитика. Можно одобрить или изменить условия (ставку считает формула, а платёж выше расчётного максимума требует комментария), запросить документы или отказать с причинами из справочника.
* Пульт администратора: ключевая ставка, сбой БКИ, режим решения, скорость конвейера, сброс данных.

## Продукты и цены

Четыре продукта и два способа расчёта: аннуитет и лимит. Все параметры лежат в [config/products.yaml](config/products.yaml).

| Продукт | Сумма | Срок | Механика | Обеспечение | Допуск |
|---|---|---|---|---|---|
| Оборотный кредит | 100 тыс. – 5 млн ₽ | 6–36 мес. | аннуитет | нет / поручительство / недвижимость | бизнесу от 6 мес. |
| Овердрафт | лимит 100 тыс. – 3 млн ₽ (≤ 50 % среднемесячных поступлений) | 12 мес., транш до 60 дней | лимит, плата за установление 1,5 % | нет / поручительство | клиент банка от 6 мес. |
| Кредит на развитие | 1 – 15 млн ₽ | 12–60 мес. | аннуитет | залог приобретаемого актива | бизнесу от 12 мес. |
| Льготный оборотный (господдержка) | 500 тыс. – 5 млн ₽ | 12–36 мес. | аннуитет, ставка **K + 3 п.п.** | как у оборотного | реестр МСП и приоритетная отрасль |

Ставка считается по одной формуле от ключевой ставки K:

`ставка = округление_вверх_до_0,5( K + OpEx + PD × LGD + плата за капитал + маржа + надбавка продукта + надбавка за срок − скидка за обеспечение )`, потолок `K + 10 п.п.`

Ставки при K = 14 % (без обеспечения, автоматическое решение):

| Грейд | Оборотный ≤ 12 мес. | Оборотный 13–36 мес. | Овердрафт | Развитие (залог оборудования) 13–36 мес. | Льготный |
|---|---|---|---|---|---|
| A | 17,5 % | 18,0 % | 18,5 % | 17,5 % | 17,0 % |
| B | 18,5 % | 19,0 % | 19,5 % | 18,5 % | 17,0 % |
| C | 20,5 % | 21,0 % | 21,5 % | 19,5 % | 17,0 % |
| D | только ручной разбор, до 24,0 % | | | | — |

Обеспечение снижает ставку, без него она выше. Поручительство даёт скидку 0,5 п.п., залог оборудования или транспорта 1,0, залог недвижимости 2,0. К ним добавляется эффект от меньших ожидаемых потерь. Для оборотного кредита на 24 месяца получается так:

| Грейд | Без обеспечения | Поручительство | Залог недвижимости |
|---|---|---|---|
| A | 18,0 % | 17,5 % | 16,0 % |
| B | 19,0 % | 18,5 % | 16,5 % |
| C | 21,0 % | 20,0 % | 17,5 % |

Название поручительства зависит от формы бизнеса. У ООО это «Поручительство собственников бизнеса», у ИП — «Поручительство третьего лица», потому что у ИП нет отдельных собственников. На цену влияет и срок: до 12 месяцев надбавка 0, от 13 до 36 месяцев +0,5, дольше +1,0 п.п. Калькулятор показывает, на сколько обеспечение снизило ставку. При изменении ключевой ставки пересчитываются все цены, а в оферте остаётся ставка на момент расчёта. Подробности в [docs/credit-policy.md](docs/credit-policy.md).

## Процесс и статусы

Клиент видит пять шагов, внутри системы 12 статусов и 26 разрешённых переходов ([диаграмма](docs/state-diagram.md), [модель процесса](docs/process-model.md)):

| Шаг | Статусы | Что происходит |
|---|---|---|
| 1. Заявка | DRAFT | создание заявки (идемпотентно), согласия |
| 2. Проверка | VERIFICATION, AWAITING_DOCS | допуск и стоп-правила, запросы в ЕГРЮЛ, ФНС, БКИ (таймаут, 2 повтора), данные банка; при нехватке данных — запрос документов |
| 3. Решение | DECISIONING, MANUAL_REVIEW, OFFER_READY, DECLINED | скоринг, платёжеспособность, цена; как просили / встречное / ручной разбор / отказ |
| 4. Подписание | AWAITING_SIGNATURE | код подтверждения (имитация простой ЭП) |
| 5. Выдача | DISBURSING, DISBURSED | договор, график платежей, моделируемое зачисление |

Завершения без выдачи: DECLINED (отказ), WITHDRAWN (клиент отозвал или отказался от предложения), EXPIRED (истёк срок документов, оферты или подписания).

## Скоринг и решение

* Скоринг и решение — разные вещи. Скоринг оценивает риск самого клиента по 14 факторам и 100 баллам и не зависит от суммы: бизнес и данные 25 баллов, денежный поток 33, кредитная история 30, налоги и репутация 12. Грейды: A от 80, B от 65, C от 50, D от 35, E ниже 35. Возраст, пол, семейное положение и регион владельца не учитываются.
* Стоп-правила срабатывают раньше скоринга, и тогда он не считается: бизнесу меньше 6 месяцев, банкротство, недостоверные сведения в ЕГРЮЛ, блокировка счетов, налоговая недоимка, текущая просрочка, иски больше 5 % оборота, санкционный флаг.
* Решение по заявке принимается в таком порядке: допуск продукта, платёжеспособность (`P_max = ЧДП / DSCR − текущие платежи`, DSCR 1,25 / 1,30 / 1,40 / 1,60 для грейдов A–D), цена, затем «как просили → больший срок → меньшая сумма → отказ». Автоматически решается заявка с грейдом A–C, данными БКИ, меньше чем двумя флагами и суммой в пределах автолимита. Остальное уходит на ручной разбор.
* Причина решения — это факторы, на которых клиент потерял больше всего баллов. Клиенту и аналитику показываются одни и те же коды причин (R01–R20), а пороги и антифрод в формулировках не раскрываются.
* Если источник данных недоступен, заявка уходит на ручной разбор, а не получает отказ.

## Архитектура

```
Браузер (статический UI, без сборки) ──► FastAPI ──► SQLite (WAL)
   кабинет клиента / рабочее место банка     │  машина состояний, журнал событий (одна транзакция)
                                             ├─ scoring.py  — карта 14 факторов, стоп-правила
                                             ├─ policy.py   — допуск, P_max по DSCR, цена, встречное предложение, маршрут
                                             ├─ pricing.py  — формула ставки, аннуитет, график
                                             ├─ mocks.py    — БКИ / ЕГРЮЛ / ФНС / данные банка (синтетика, управляемые сбои)
                                             └─ cascade.py + pd_provider.py — опциональный ML-слой
```

* Журнал событий (`events`) общий: клиент видит свою часть, банк — всю.
* Надёжность и безопасность. Статус меняется только по таблице переходов, заявка защищена от одновременных правок (поле `version`), создание заявки идемпотентно (`Idempotency-Key`). Есть роли `client`, `analyst`, `admin`, и клиенты не видят чужих данных. Пароли хранятся как PBKDF2, число неудачных входов ограничено (8 за 5 минут на логин), длина текстовых полей ограничена. Контейнер работает не от root, у него есть healthcheck, а статика всегда проверяется заново (`Cache-Control: no-cache`).
* Политика лежит в конфиге: продукты, формула цены, грейды и DSCR в [config/products.yaml](config/products.yaml). Версии карты и политики записываются в каждое решение.

Подробности про контейнеры, последовательность вызовов, ER-модель и то, что менять в проде: [docs/architecture.md](docs/architecture.md).

## Тесты и проверка цифр

* `pytest -q` проверяет скоринг, цену и политику, сквозные сценарии четырёх клиентов через HTTP, права доступа, идемпотентность, то, что клиенту не попадают внутренние данные, и каскад. Тестам ML-конвейера нужен LightGBM, поэтому их запускают в контейнере из `ml/Dockerfile`.
* `python tests/verify_numbers.py` отдельно пересчитывает цены (1120 сочетаний продукта, грейда, срока и обеспечения), аннуитет, график платежей и `P_max` по формулам из документации.

## ML-слой (опционально)

Второй режим решения, `ml_cascade`. Одна модель градиентного бустинга (LightGBM) на все продукты оценивает вероятность дефолта для конкретного предложения. У каждого продукта два порога, по ним заявка попадает в автоодобрение, серую зону или пропуск продукта. В серой зоне сначала пробуются более безопасные продукты, а если ни один не подошёл, заявку берёт живой верификатор. Стоп-правила работают до модели.

Обученной модели в репозитории нет, потому что данных банка у нас нет. Без неё вероятность дефолта считается по скоркарте, и всё остальное работает как обычно. Скрипты обучения и предсказания ([`ml/train.py`](ml/train.py), [`ml/predict.py`](ml/predict.py)) проверены только на синтетических данных. Подробности: [docs/ml.md](docs/ml.md).

## Что не вошло в эту версию (и почему)

Мы не стали делать LLM-подбор продукта «своими словами», прогноз кассового разрыва и разбор выписок. Основа решения детерминированная и проверяемая, а ИИ остаётся опциональным слоем на будущее. Не вошли и настоящие электронная подпись и интеграции, кредитный комитет (вместо него поле `second_approver_required`), обслуживание кредита сверх модуля «Мой кредит». Вместо PostgreSQL используется SQLite: схема совместима, в проде её нужно заменить. Откуда взяты допущения и чем они ограничены, написано в [docs/assumptions.md](docs/assumptions.md).
