# Ввод модуля в эксплуатацию и встраивание в системы банка

Документ для команды внедрения: что представляет собой модуль, как он встраивается в ландшафт банка, в каком порядке подключать источники и переводить решения с синтетики на реальные данные. Технические детали прототипа — в `architecture.md`, источники — в `data-sources.md`, API — `/docs` (OpenAPI) и `api-examples.http`.

## 1. Что внедряется

Модуль «Умный кредитный кабинет» состоит из четырёх слоёв с чёткими границами:

| Слой | Код | Роль в бою |
|---|---|---|
| Клиентский кабинет (раздел «Кредиты») | `static/` | встраивается в Альфа-Бизнес как раздел или микрофронтенд; работает только через REST |
| Рабочее место аналитика | `static/` (роль `analyst`/`admin`) | очередь, карточка, решение, журнал; встраивается в операционный портал банка |
| Сервис решений | `app/states.py`, `scoring.py`, `policy.py`, `pricing.py`, `reasons.py`, `service.py` | машина состояний заявки, скоркарта, политика, цена, единые причины для клиента и аналитика |
| «Умный» слой | `app/smart.py` (радар, лимит), `ml/` (PD-модель, опционально) | прогноз кассового разрыва, единый лимит, предложения до заявки |

Все слои говорят между собой только через API и единый профиль клиента (`scoring.build_profile`). Адаптеры источников (`app/mocks.py` в демо) — единственное место, где синтетика заменяется реальными системами.

## 2. Целевая схема встраивания

```
Альфа-Бизнес (web/mobile) ──SSO (Alfa ID / OIDC)──▶ API модуля ──▶ Сервис решений ──▶ Адаптеры ──▶ БКИ · ФНС · ЕГРЮЛ · ФССП/КАД · АБС · Alfa API
        │                                              │                 │
        └── раздел «Кредиты» (iframe / MF)             │                 └── Очередь задач (воркеры конвейера)
Операционный портал банка ──▶ Рабочее место аналитика  └── PostgreSQL · Redis · Аудит-лог (WORM) · Шина событий (статусы, уведомления)
```

- **Аутентификация.** Вместо локальных логинов — OIDC через Alfa ID (клиенты) и корпоративный SSO (сотрудники); роль и `client_id` приходят в токене. В коде это замена `auth` в `app/main.py` и `db.users`; маршруты и проверки ролей (`client_only`, `bank_only`) остаются.
- **Данные клиента.** `client_id` модуля = идентификатор клиента в CRM/АБС банка. Карточка компании (`profile.company`) читается из мастер-данных банка, а не из мока.
- **События.** Переходы статусов (`service.move`) публикуются в шину событий банка: push и уведомления в приложении, CRM, антифрод. Внутренняя лента и колокольчик кабинета подписаны на те же события.
- **Хранилище.** PostgreSQL вместо SQLite (схема в `db.py` совместима: заявки, события, пользователи, счета); сессии и лимиты входа — Redis; журнал решений — неизменяемый (WORM) с версией карты и политики в каждой записи.
- **Исполнение конвейера.** Шаги `step_verify → step_decide → …` переносятся из потока на заявку в очередь задач (arq/Celery/Kafka-консьюмер); `resume_pending` запускается в одном экземпляре. Деградация источника в ручной разбор (`_degrade`) сохраняется как бизнес-правило.

## 3. Порядок подключения источников (от минимума к полному)

| Этап | Что подключаем | Что начинает работать на реальных данных |
|---|---|---|
| 0. Пилот на синтетике | ничего (моки) | проверка UX, процесса, рабочего места; обучение аналитиков |
| 1. Собственные данные банка | АБС: обороты за 12 мес., остаток, платёжный календарь; мастер-данные клиента | скоринг 2.x, P_max, предодобрение, **Финансовый радар**, **Умный лимит**, «Мои кредиты» |
| 2. Государственные реестры | ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», реестр МСП, ФССП, КАД | стоп-правила, скоринг 1.1 и 4.x, репутация в радаре, льготная программа |
| 3. Кредитные бюро | НБКИ/ОКБ по согласию клиента | скоринг 3.x, платёжная нагрузка, рост лимита «дисциплина»; деградация в ручной разбор при сбое |
| 4. Внешние обороты | выписки других банков (файл, Open API), Alfa API для клиентов на других счетах | фактор подтверждённости данных, рост лимита «выписка», точность радара для новых клиентов |
| 5. Обеспечение и подпись | оценка залога, реестр залогов, ЕГРН; ЭП через Госключ/КЭП; выдача через АБС | ставка с обеспечением, `AWAITING_SIGNATURE → DISBURSING → DISBURSED` как реальные операции |
| 6. Рыночные данные | Пульс рынка (эквайринг по отраслям), отраслевые бенчмарки портфеля, ключевая ставка ЦБ | фактор «рынок» в радаре, маржа отрасли из факта, автоматическое обновление цены |

Каждый этап можно включать независимо: адаптер отвечает `UNAVAILABLE` — и решение честно уходит в ручной разбор, а не ломается.

## 4. Перевод решений с синтетики на реальные данные

1. **Теневой режим (shadow).** Модуль считает решение параллельно действующему процессу, но не выдаёт его клиенту: сравниваем исходы, калибруем пороги грейдов и автолимиты (`config/products.yaml`).
2. **Калибровка карты.** Экспертная скоркарта валидируется на портфеле (Gini, PSI по факторам); при наличии истории дефолтов обучается PD-модель (`ml/train.py`) и включается каскад `DECISION_MODE=ml_cascade` как претендент (champion/challenger).
3. **Пилот на когорте.** Авто-решения для грейдов A–B и сумм внутри автолимита; всё остальное — аналитику. Метрики: доля авто-решений, время до решения, доля дозапросов, принятие встречных предложений, дефолтность когорты.
4. **Расширение.** Поднимаем автолимиты и добавляем продукты по результатам пилота; радар переводим с формулы на ML-прогноз той же сигнатуры, когда накопятся данные.

Все пороги, ставки, отрасли и тексты причин — конфигурация (`config/products.yaml`, `app/reasons.py`), версионируются и фиксируются в каждой заявке; смена политики не трогает код.

## 5. Безопасность и комплаенс

- Клиенту не раскрываются внутренние пороги: из клиентских ответов убрать `p_max`, `max_amount`, `headroom`, `grade` (сейчас частично в `/api/client/quote`), оставить «укладывается / комфортная сумма».
- Причины отказа по стоп-правилам ФНС и санкционным спискам — только нейтральные формулировки, согласованные с юристами; детали — в ручном разборе.
- Токены — httpOnly cookie, CSP, CSRF; код подписи — не в ответе API, а через канал банка; ограничение попыток.
- Маскирование ПДн по роли, журнал просмотров аналитика, матрица полномочий (аналитик до X, старший до Y, комитет выше) вместо флага `second_approver_required`.
- 115-ФЗ: отдельный статус комплаенс-проверки и обязательное участие уполномоченного сотрудника.

## 6. Эксплуатация

- **Поставка.** Контейнер из `Dockerfile`, конфигурация через переменные окружения (`PORT`, `KEY_RATE`, `STEP_DELAY_SEC`, `DECISION_MODE`, `DEMO_MODE=0` для прода), healthcheck `/api/health/ready`; в k8s — два деплоя: API и воркер конвейера.
- **Наблюдаемость.** Метрики по этапам конвейера, доля деградаций по источникам, время ответа адаптеров; алерты на недоступность источника; трассировка заявки по `app_id` через журнал событий.
- **Тесты как контракт.** `pytest` (107 сценариев, включая сверку 1120 ценовых комбинаций) запускается в CI на каждое изменение политики; тест-сценарии — `test-scenarios.md`.
- **Поддержка аналитиков.** Пульт администратора: ключевая ставка, режим БКИ, скорость конвейера; в проде — только через процедуру изменения политики с двумя подтверждениями.

## 7. Чек-лист готовности к бою

- [ ] SSO и мастер-данные клиента подключены, локальные учётки отключены (`DEMO_MODE=0`)
- [ ] PostgreSQL, Redis, очередь; `resume_pending` в одном экземпляре
- [ ] Адаптеры этапов 1–3 с таймаутами и circuit breaker; деградация проверена
- [ ] Клиентские ответы без внутренних полей; нейтральные причины согласованы
- [ ] Матрица полномочий и комплаенс-статус включены
- [ ] Теневой режим пройден, пороги откалиброваны, метрики пилота на дашборде
- [ ] Аудит-лог неизменяем, версии карты и политики в каждой заявке
- [ ] Радар и лимит читают реальные обороты и график; источники из `data-sources.md` отмечены как подключённые
